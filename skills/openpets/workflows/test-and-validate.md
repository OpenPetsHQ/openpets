# Test and Validate an OpenPets Plugin

Use this workflow after changing plugin behavior and before local sharing,
submission, packaging, or catalog release.

## Test behavior with the SDK harness

Scaffolded plugins include `test.js`. Keep tests deterministic with
`@open-pets/plugin-sdk/testing`:

- create a harness from the plugin's `register` function;
- drive time, events, commands, and assistant capabilities through the harness;
- assert the visible host descriptors and durable state the user cares about;
- cover restart/reconciliation behavior when the plugin uses schedules or
  storage.

Do not add Electron, live network, timing, or pixel tests for ordinary plugin
logic. The harness exists so plugin behavior can be tested without a running app.

Run the plugin test using the command generated by the scaffold or the package's
documented test command. In the OpenPets repository, `pnpm plugins:test` runs
locale checks and the official/community plugin harness suites.

## Validate the distributable folder

Run this for every standalone plugin change:

```bash
openpets plugin validate <plugin-directory>
```

It catches manifest shape, SDK compatibility, permissions, config field types,
network declarations, assets, panels, and referenced files before the desktop
loader sees the plugin. Fix the validation error at its source; do not weaken the
manifest merely to suppress it.

After validation, local-load the plugin and verify the changed user-facing path
in the desktop app. Local validation and local loading are sufficient for normal
plugin iteration.

## Separate local work from catalog release

Only use the following repository-root commands for a maintainer preparing a
reviewed catalog release:

```bash
pnpm plugins:check
pnpm plugins:package
pnpm plugins:validate-release
```

`plugins:package` creates catalog/ZIP staging; it does not publish. Release
validation is the pre-ship gate because it catches catalog/package drift,
missing locale and asset files, missing ZIPs, and SHA mismatches. Uploading and
deploying are explicit later actions, never a consequence of loading a local
plugin.
